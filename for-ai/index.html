Knowledge model

Use Domain → Topic → Hack → Protocol as the primary practical stack. Add a Method when a named structured approach is used, and a Lens when the content borrows a way of thinking from a discipline, profession, philosophy, or strategic tradition. Methods and Lenses are classification dimensions, not substitutes for the user's concrete Topic and not evidence by themselves.

Legacy Life Area and Growth Zone fields remain for compatibility. Use ontology.json to resolve each old Growth Zone to a Topic, Method, or Lens rather than assuming all old zones are the same kind of thing.

For recommending published knowledge

  1. Identify the concrete Topic that matches the user's need; use the Domain only as a broad navigation layer.
  2. Retrieve a few protocols from the trusted feed.
  3. Prefer reviewed or practical entries.
  4. Use Method and Lens metadata to refine the approach, not to inflate evidence.
  5. Show the action, evidence state, Brali page, and direct sources for reviewed research-derived material.

For improving Brali

Use a different path: research candidate → evidence decision → hack → protocol → ontology → publish. Search output is deliberately not publishable evidence.

  1. Load Research Discovery and add deduplicated leads to the candidate queue.
  2. Load Evidence Review, read the actual source, and record what it really supports or challenges.
  3. Use Protocol Design only after the atomic action and its evidence boundary are clear.
  4. Use Taxonomy Curation to assign Domain/Topic and optional Method/Lens tags without inventing unnecessary categories or breaking legacy URLs.

Machine-readable files

  • ontology.json — Domains, Topics, Methods, Lenses, and the complete legacy Growth Zone map.
  • protocols.json — trusted protocol feed.
  • hacks.json — broader library corpus.
  • evidence.json — evidence and review status.
  • review-queue.json — existing content needing review.
  • research-queries.json — maintained research lenses.
  • research-candidates.json — unreviewed scholarly leads.
  • agents/registry.json — agent roles and skill paths.
  • indexing.json — discovery status.
  • llms.txt — project guide for language-model tools.

Contracts

  • Hack — one reusable practical action with optional domain_slugs, topic_slugs, method_slugs, and lens_slugs.
  • Protocol — one or more actions with ordering, check-in, review/stop logic, and the same ontology fields.
  • Research Candidate — discovery metadata only.
  • Evidence Decision — traceable result of reading the actual source.

Evidence boundary

A source being present is not the same as a source being reviewed. A DOI, title, abstract, citation count, search rank, or AI summary cannot promote an item to reviewed. A Method name or professional Lens also provides no evidence by itself.

Do not erase uncertainty

Keep the evidence state, source scope, and important limitations when reusing Brali content. Do not turn a practical suggestion into a scientific claim or make a narrow study sound universal.

MCP

The JSON files and contracts are the public interface today. A future MCP service can add search, read, recommendation, and ontology tools over the same canonical data instead of creating a second knowledge model.
