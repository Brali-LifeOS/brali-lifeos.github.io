For recommending published knowledge

  1. Find the Life Area or Growth Zone that matches the user's need.
  2. Retrieve a few protocols from the trusted feed.
  3. Prefer reviewed or practical entries.
  4. Show the action, evidence state, and Brali page.
  5. If a reviewed entry has evidence.source_url, keep that link with the answer.

For improving Brali

Use a different path: research candidate → evidence decision → hack → protocol → taxonomy → publish. Search output is deliberately not publishable evidence.

  1. Load Research Discovery and add deduplicated leads to the candidate queue.
  2. Load Evidence Review, read the actual source, and record what it really supports or challenges.
  3. Use Protocol Design only after the atomic action and its evidence boundary are clear.
  4. Use Taxonomy Curation to map the result without inventing unnecessary zones or breaking URLs.

Machine-readable files

  • protocols.json — trusted protocol feed.
  • hacks.json — broader library corpus.
  • evidence.json — evidence and review status.
  • review-queue.json — existing content needing review.
  • research-queries.json — maintained research lenses mapped to taxonomy.
  • research-candidates.json — unreviewed scholarly leads.
  • agents/registry.json — agent roles and skill paths.
  • indexing.json — discovery status.
  • llms.txt — project guide for language-model tools.

Contracts

  • Hack — one reusable practical action.
  • Protocol — one or more actions with ordering, check-in, and review/stop logic.
  • Research Candidate — discovery metadata only.
  • Evidence Decision — traceable result of reading the actual source.

Evidence boundary

A source being present is not the same as a source being reviewed. A DOI, title, abstract, citation count, search rank, or AI summary cannot promote an item to reviewed.

MCP

The JSON files and contracts are the public interface today. A future MCP service can add search, read, and recommendation tools over the same canonical data instead of creating a second knowledge model.
