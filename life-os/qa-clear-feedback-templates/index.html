Write an Actionable QA Report Another Person Can Use

State the observed behavior, reproduction context, evidence, and acceptance check.

Protocol summary · practical

Try this

Write a one-line observed problem and context, add the smallest reliable reproduction sequence, attach the relevant evidence while removing secrets and personal data, label any suspected cause as a hypothesis, state the expected behavior, and define a narrow acceptance check for the fix.

Check-in: Can another person see what happened, reproduce or investigate it, distinguish fact from hypothesis, and know what would count as fixed?

Evidence: Practical guidance; no evidence-like claim is detected in the current source record.

Review note: The inherited QA article contained fabricated engineering results, unsupported cycle-time reductions, pseudo-optimal evidence quantities, invented social effects, and universal prescriptions. The effective public record is a defect-reporting handoff: observable behavior, relevant context, reliable reproduction information, focused redacted diagnostics, explicitly labeled hypotheses, expected behavior, and a narrow acceptance check.

A defect report is a handoff. Its job is to make the next investigation cheaper and safer, not to prove that the reporter already knows the cause. A compact report keeps observations, reproduction context, hypotheses, and acceptance criteria distinct.

1. Start with the observable problem

Write one sentence describing what happened and where: feature, environment, relevant state, and visible failure. Avoid blame and avoid explaining the cause before the behavior itself is clear.

2. Add the smallest reliable reproduction context

List the prerequisites, inputs, and sequence needed to encounter the problem. Include version, platform, account state, feature flag, or sample data only when it matters. Say when the issue is intermittent rather than presenting one occurrence as a deterministic sequence.

3. Attach focused diagnostic material

Add the screenshot, request identifier, trace excerpt, console output, or other artifact that helps locate the failure. Remove secrets and unrelated personal data. Put suspected causes in a separately labeled hypothesis so the receiver can challenge them without disputing the observation.

4. State expected behavior and the acceptance check

Describe what should happen instead and the narrow condition that would demonstrate the fix in the reported context. If broader regression coverage is needed, keep that as a separate verification task rather than expanding the original defect indefinitely.

Questions to consider

Should every bug report include a suspected cause?

No. Add a hypothesis only when you have a useful reason for it, and label it clearly. A precise observation with reproducible context is better than a confident guess.

How much log or trace data should I attach?

Include enough to identify the failing behavior and relevant context without burying the report. Remove credentials, tokens, personal data, and unrelated payloads before sharing diagnostic material.

Try it, then review.

Use the action above as a starting point. Adapt it to your situation, notice what happens, and keep, change, or drop it.
